======================================================================
一、整改目标
======================================================================

本轮不继续扩展新概念页面，集中补齐任务书中已经要求、但尚未形成真实业务闭环的功能：

1. 成员 A：会话管理、系统设置、统一舆情安全、操作审计。
2. 成员 B：接口绑定、Skills 真实生效、TTS 配置贯通、真实多模态任务。
3. 成员 C：采集任务生命周期、瞭源运行指标、数据仓库完整操作。
4. 所有功能必须基于真实数据库或真实接口，不使用随机数、模拟成功结果或假资源地址。
5. 所有数据库变化必须使用新迁移文件，禁止修改已经合并的旧迁移文件。

======================================================================
二、分支和协作规则
======================================================================

1. 统一基线

   所有人先获取合并后的 main：

   git fetch origin
   git checkout main
   git pull --ff-only origin main

   确认 HEAD 不低于：1a57b0d

2. 分支安排

   集成整改分支：integration/v0.3-gap-fix
   成员 A 分支：fix/member-a-platform-closure
   成员 B 分支：fix/member-b-ai-closure
   成员 C 分支：fix/member-c-collection-closure

   三个成员分支都必须从 integration/v0.3-gap-fix 创建，禁止从旧成员分支继续开发。

3. 数据库迁移编号预留

   成员 C：023—029
   成员 B：030—039
   成员 A：040—049

   未使用的编号可以留空，禁止抢用其他成员区间，禁止再出现多个 007、008 之类的重复版本。

4. 推荐合并顺序

   第一批：成员 C
   第二批：成员 B
   第三批：成员 A
   最后：集成回归、演示数据和 main 发布

   原因：B 的数据分析师和数据库问数依赖 C 的稳定查询接口；A 的统一舆情与审计需要接入 B、C 最终确定的业务入口。

5. 公共文件修改规则

   app.py、migration_runner.py、seed.py、base 模板等公共文件尽量由各成员在自己的提交中最小化修改。
   修改公共接口时，必须同步更新 docs/API_CONTRACT.md 或在提交说明中写明请求和响应结构。
   不允许用整文件覆盖的方式解决冲突。

三、成员 A 整改任务
负责人范围：平台、权限、会话、设置、舆情安全、系统操作审计
======================================================================

A-1 会话与消息管理闭环（P0）

当前问题：
1. 目前仅支持用户和关键词筛选。
2. 后台分页 total 使用当前页数量，页数不正确。
3. 缺少归档、后台导出、风险和模型调用指标。

必须完成：
1. 会话列表支持按用户、开始时间、结束时间、模型、数字员工、状态筛选。
2. Repository 返回“当前页数据 + 符合条件的总数”，修复后台分页。
3. 会话详情显示完整消息、风险等级、命中敏感词、模型耗时和 Token 消耗。
4. 支持单条删除、批量删除和归档/取消归档。
5. 支持管理员导出指定会话，优先复用现有 PDF 导出服务。
6. 所有查询使用参数化 SQL，普通用户仍只能访问自己的会话。

验收：
1. 制造超过 20 条会话后分页总数和页数正确。
2. 不同筛选条件能得到正确结果。
3. 普通用户修改 URL 不能查看其他用户会话。
4. 归档、删除和导出均有明确成功或失败提示。

A-2 系统设置真实生效（P0）

必须完成：
1. 为 boolean、integer、string 等设置建立统一类型校验。
2. 对刷新间隔、采集超时、最大采集数量、上传大小等数值设置增加合法范围。
3. 设置修改后必须由实际业务代码读取，不能只改变管理页面显示。
4. 敏感配置只保存环境变量名称或掩码，不保存和回显真实密钥。
5. 每次设置修改写入操作审计日志，记录修改人、设置项和修改时间。
6. 与成员 B 约定 TTS 设置边界：A 负责公共设置校验和审计，B 负责 TTS 运行服务读取数据库配置。

A-3 统一舆情安全链路（P0）

对外提供稳定服务方法：

OpinionSecurityService.analyze_and_record(
    source_type,
    source_id,
    content,
    user_id=None,
    metadata=None
)

必须接入：
1. 用户提问。
2. 普通模型回复。
3. 数字员工回复。
4. 采集新闻标题和正文。
5. 新闻摘要、文案生成结果。

必须记录：
1. 内容来源和来源 ID。
2. 命中敏感词。
3. 风险等级和 AI/规则分析结果。
4. 创建时间、处理状态、处理人、备注和处理时间。
5. 相同来源内容避免重复生成相同预警。

分工边界：
1. A 提供统一服务和数据表。
2. B 在模型、数字员工和文案输出位置调用。
3. C 在采集内容入仓位置调用。

A-4 操作与安全审计（P0）

必须完成：
1. 用户、角色、功能、菜单、接口、Skills、数字员工、模型、数据源、仓库、设置的新增/编辑/删除/启停操作写入 AuditLogService。
2. 日志包含操作人、操作类型、资源类型、资源 ID、结果、IP、时间和错误信息。
3. 审计写入失败不能破坏原业务事务，但必须写入 error.log。
4. 审计列表支持按操作类型、用户、资源和时间查询。

A-5 外部代码审计说明（本轮不执行）

1. 代码审计报告和漏洞扫描后续独立安排。
2. 本轮不要求 A 编写修复前/后审计报告，也不要求现在生成漏洞整改清单。
3. 扫描、报告整理和后续漏洞整改另行安排，不作为本轮 A/B/C 功能整改的合并阻塞项。
4. A 当前仍需完成 A-4 所述的“系统操作与安全审计功能”，该模块属于项目业务功能，与外部代码扫描不是同一任务。

A 提交要求：
1. 提交信息建议：fix(platform): complete session security and audit workflows
2. 新增会话权限、分页、设置校验、舆情记录和审计日志测试。
3. 不修改 B、C 已稳定的业务算法，只在约定入口接入统一服务。

四、成员 B 整改任务
负责人范围：数字员工、接口、Skills、模型、TTS、多模态
======================================================================

B-1 接口与数字员工真实绑定（P0）

当前问题：接口管理和数字员工管理各自存在，但运行时没有真正绑定。

必须完成：
1. 为数字员工增加 interface_id，或建立 employee_interfaces 绑定表。
2. 后台可以选择数字员工绑定的接口。
3. 接口型数字员工执行时从 InterfaceRepository 读取 URL、方法、请求头、参数、响应路径、超时和重试次数。
4. 统一保留 SSRF、防私网/回环、响应大小、敏感请求头和环境变量密钥保护。
5. 接口停用后，关联数字员工返回明确的“接口已停用”提示。
6. 接口调用结果和失败原因写入 interface_calls 和数字员工调用日志。

B-2 Skills 必须真实生效（P0）

当前问题：可以管理和绑定 Skill，但 DigitalEmployeeService 不读取绑定结果。

必须完成：
1. DigitalEmployeeService 执行前读取该员工已启用的绑定 Skills。
2. prompt 类型 Skill 必须改变最终系统提示词，并在调试日志中记录生效的 Skill 编码。
3. tool 类型 Skill 必须调用明确的后端工具服务，不能只拼接一段说明文字。
4. 至少完成一个可现场演示的“数据库问数 Skill”：调用成员 C 的 QueryIntentService，返回结论、KPI、图表和表格结构。
5. Skill 停用或解除绑定后，员工行为立即恢复，不需要重启服务。
6. 前端响应中可显示本次使用的 Skill 名称，但不能暴露完整系统提示词。

验收演示：
1. 数据分析师未绑定 Skill 时返回普通提示。
2. 绑定数据库问数 Skill 后，对“各来源有多少条新闻”返回真实仓库统计。
3. 停用 Skill 后不再执行问数工具。

B-3 TTS 配置链路统一（P0）

当前问题：后台保存到 tts_config，TTSService 却读取静态配置文件。

必须完成：
1. TTSService.get_config() 以 TTSConfigRepository 为唯一运行时配置来源。
2. API Key 和 Secret 仅保存环境变量名称，运行时再读取环境变量值。
3. 后台修改启用状态、供应商、默认声音、语速、音量、音调后立即生效。
4. 保留长文本分段、缓存、audio_url 和失败时继续显示文字。
5. 后台预览和用户侧播放必须经过同一 TTSService。
6. 调用成功、失败、耗时、缓存命中写入 tts_calls。

B-4 生图、生视频和多模态真实任务（P0）

当前问题：服务使用同步 requests、默认不可验证地址和文件 JSON 状态，未形成数据库闭环。

必须完成：
1. 使用 Tornado AsyncHTTPClient 或其他异步客户端，禁止在异步 Handler 内使用同步 requests。
2. MultimodalService 从 MultimodalConfigRepository 读取配置。
3. 任务统一写入数据库 multimodal_tasks，不再以文件 JSON 作为主状态。
4. 提交任务、轮询状态、完成、失败和删除均操作数据库记录。
5. 接入至少一个真实可配置的 OpenAI API 兼容生图服务。
6. 生视频如果演示环境没有真实服务，必须明确显示“未配置/不可用”，禁止返回模拟视频地址或假成功。
7. 真实生成结果保存供应商任务 ID、资源 URL、耗时和失败原因。
8. API Key 使用环境变量，日志和页面不得显示明文。
9. 用户侧图片、视频卡片使用真实任务结果；失败时显示可理解的错误。

B-5 模型与日志收尾（P1）

1. 模型测试、数字员工、Skills、TTS、多模态全部记录调用次数、耗时、Token 或错误原因。
2. 清理不可验证的默认服务地址。
3. 补充接口绑定、Skills 生效、TTS 配置、多模态任务状态和 SSRF 测试。

B 提交要求：
1. 提交信息建议：fix(ai): activate skills interfaces tts and multimodal workflows
2. 不得提交真实 API Key。
3. 不得用模拟 URL 或固定成功数据通过测试。

五、成员 C 整改任务
负责人范围：采集源、采集任务、数据仓库、数据库问数
======================================================================

C-1 统一采集任务状态和表结构（P0）

当前问题：数据库只允许 pending/running/success/failed，服务会写 paused/partial。

统一状态建议：
1. pending：等待执行
2. running：正在执行
3. success：全部成功
4. partial：部分成功
5. failed：全部失败或任务异常
6. cancelled：用户取消

必须完成：
1. 使用 023 号起的新迁移安全升级 collection_runs，保留旧数据。
2. 不再混用 paused 表示取消；取消统一为 cancelled。
3. 增加进度、成功数、失败数、总数、开始时间、结束时间和最近错误等必要字段。
4. 服务、Repository、页面和测试共用同一状态枚举。

C-2 采集任务完整生命周期（P0）

必须增加后台路由和页面：
1. 任务列表。
2. 创建批量采集任务。
3. 创建单条采集任务。
4. 查看进度。
5. 查看分步骤日志。
6. 查看采集结果。
7. 取消 pending/running 任务。
8. 失败任务重试。
9. 服务启动后的中断任务恢复。

要求：
1. 单个来源失败不能导致整个批量任务崩溃。
2. 部分成功必须记录为 partial，并保留已成功数据。
3. 重试不能重复写入相同结果。
4. 页面必须显示真实进度和日志，不使用前端计时器伪造进度。

C-3 瞭源运行指标（P0）

在来源列表中补齐：
1. 最近采集时间。
2. 成功次数和失败次数。
3. 成功率。
4. 最近失败原因。
5. 最近耗时。
6. 手动执行采集入口。

指标必须由 collection_runs 聚合，不在模板中写固定值。

C-4 数据仓库完整操作（P0）

必须完成：
1. 来源筛选。
2. 开始时间和结束时间筛选。
3. 单条查看。
4. 单条重新采集。
5. 批量删除。
6. 批量深采和深采日志。
7. 风险等级筛选。
8. CSV 或 JSON 数据导出。
9. 显式去重，并保证重复导入幂等。
10. 所有查询分页并使用参数化 SQL。

C-5 数据库问数与成员 B 的接口约定（P0）

稳定对外方法：

QueryIntentService.query(question, user_id=None)

统一返回：
1. intent：命中的意图编码。
2. conclusion：自然语言结论。
3. kpis：KPI 列表。
4. charts：折线图、柱状图或环形图数据。
5. table：表头和明细。
6. generated_at：生成时间。

保留任务书七类真实问题，禁止模型生成任意 SQL 后执行，禁止字符串拼接 SQL，禁止随机统计结果。

C-6 舆情联动（P1）

1. 采集标题、正文和摘要入仓后调用成员 A 的 analyze_and_record 服务。
2. 仓库项目保存风险等级、命中词和安全分析摘要。
3. 同一采集结果重复导入时不重复生成预警。

C 提交要求：
1. 提交信息建议：fix(collection): complete task lifecycle and warehouse operations
2. 增加状态迁移、任务取消/重试/恢复、来源指标、仓库筛选/导出和七类问数测试。
3. crawl4ai 必须保留，采集失败必须有明确日志。

六、跨成员接口冻结
======================================================================

为减少再次合并冲突，以下接口一经确认不得随意改名：

1. C 提供：QueryIntentService.query(question, user_id=None)

如确需改变接口：
1. 先更新 docs/API_CONTRACT.md。
2. 同时修改调用方和测试。
3. 在提交说明中列出兼容影响。

======================================================================
八、完成判定
======================================================================

仅创建页面、表结构、按钮或占位服务不算完成。

一个功能只有同时满足以下条件才可标记完成：

1. 前端可以操作。
2. 后端接口真实执行。
3. 数据正确落库或来自真实接口。
4. 权限和安全校验生效。
5. 成功与失败均有可理解反馈。
6. 自动化测试覆盖关键路径。
7. 能在合并后的完整项目中现场演示。

本轮目标是补齐现有任务书，不继续无限增加新模块。
