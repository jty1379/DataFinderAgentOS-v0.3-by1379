# 产品需求与变更记录

## R1 · v0.1 基线

- R1.1 保持 Tornado MVC 项目结构、`app.py` 入口和默认端口 `10010`。
- R1.2 用户注册、登录、退出；用户侧和管理侧账号隔离。
- R1.3 Secure Cookie、XSRF、SQL 参数化和 PBKDF2-SHA256 密码哈希。
- R1.4 用户、角色、功能、菜单管理及动态菜单权限链路。
- R1.5 Layui/Bootstrap 本地化，支持 PC 和移动端。

## R2 · 任务 2 权限管理完整实现

### R2.1 用户管理

- 集中管理普通用户与管理侧账号，支持列表、搜索、新增、修改、删除、启用、禁用和批量操作。
- 固定每页 20 条，页面采用上（搜索与批量操作）、中（列表）、下（分页）三段式布局。
- 用户与角色为一对一关系；创建或修改账号时必须选择一个有效角色。
- 只有默认超级管理员 `admin` 可以执行写操作。拥有 `user_management` 的其他管理角色可以登录后台并查看、搜索用户，但构造新增、修改、删除、启停、批量操作请求时必须返回 403。
- 任务 2.1 验收账号 `useradmin / admin888` 使用 `useradmin` 管理侧角色并授予用户管理功能后，必须能够登录后台和打开用户管理页，且保持只读。

### R2.2 角色管理

- 内置角色包括普通用户（只能登录用户侧）与系统管理员（只能登录管理侧）。
- 支持自定义角色列表、搜索、新增、修改、删除、启停和每页 20 条分页，布局与用户管理一致。
- 内置系统管理员角色的编码、名称、访问端、状态及功能授权均不可编辑，也不可删除；Repository 与 Handler 双层保护。
- 角色与功能通过 `role_features` 多对多关联，授权界面使用 Layui Tree 的树形勾选方式；禁用功能在授权树中不可勾选。

### R2.3 功能与菜单管理

- 功能管理支持列表、搜索、新增、修改、删除、启停和每页 20 条分页，页面布局与用户管理一致。
- 功能数据包含图标、名称、路由地址、排序值及父功能；只允许“一级功能 + 二级功能”两层结构，禁止自引用、循环引用和第三级。
- 功能禁用后，角色授权判定和菜单生成立即忽略该功能，角色授权界面也不允许新选中它。
- 菜单一对一绑定功能，支持有限的显示/隐藏、排序和预览操作。用户最终看到的左侧菜单由“角色授权 ∩ 功能启用 ∩ 菜单显示”实时生成。

### R2.4 超级管理员保护（任务 2.2 / 2.4）

- 默认 `admin` 账号首次初始化后不重复创建，也不重置已有密码。
- 任何账号（包括 `admin` 自己）都不能修改 `admin` 的用户名、角色和状态，也不能删除或通过批量操作影响该账号。
- 仅 `admin` 本人可以在专用表单中验证当前密码后修改自己的密码；该表单不包含用户名、角色或状态字段。
- 其他管理角色即使获得用户管理功能，也只能查看，不能修改 `admin` 或其他账号。
- 当前账号和最后一个可用管理账号继续受到停用、降级和删除保护。

### R2.5 导航可读性（任务 2.3）

- 修复管理端右上角用户下拉菜单文字与背景对比不足的问题，不能出现白字白底。
- 下拉菜单支持鼠标、键盘、清晰焦点状态以及不小于 24px 的操作目标。

## R3 · 瞭源、采集与数据仓库

### R3.1 瞭源管理

- 管理采集来源与规则，支持新增、修改、删除、查询、启停、列表和分页。
- 规则包含目标 URL、请求方法、安全请求头和参数定义。
- 参数定义支持关键词、页码、步长和固定参数，并可在采集页面可视化配置。
- RequestHeaders 中的 Cookie、Authorization 等敏感字段不得保存或转发。

### R3.2 瞭望采集

- 原“瞭望管理”更名为“瞭望采集”。
- A 区为水平居中的关键词输入和采集按钮。
- B 区为可用瞭源规则及其参数配置，布局稳定且不挤压换行。
- C 区展示真实采集结果，PC 一行三列、每页 12 条并支持分页。
- 超时、站点拒绝、解析失败和无结果必须给出明确结论。
- 百度新闻使用无 Cookie、低频请求进行联调；自动测试不依赖其在线状态。
- 2026-07-13 冒烟测试以“四川”、`pn=0` 和公开浏览器兼容头请求百度新闻，HTTP 200、约 542,548 字节；项目内 `CollectorService.collect` + 临时数据库默认规则实测得到 `RULES 1`、`RESULTS 10`，真实标题和 HTTPS 地址均能进入规范化结果。仅最小 User-Agent 的对照请求进入 `wappass` 图形验证码。
- 百度新闻当前可用但受请求头和站点风控影响，只作为教学联调来源；实现必须检测验证码、重定向和空结果，不能将其承诺为稳定生产接口。

### R3.3 数据仓库与深度采集

- C 区支持勾选和全选当前页，将选中结果批量保存到数据仓库。
- 数据仓库支持搜索、分页、详情查看和删除。
- 列表显示来源、采集时间及“是否深度采集”标识。
- 重复保存同一条业务数据必须幂等。
- 单条与批量深采由系统“采集专员”执行；已完成数据支持更新采集。
- 悬浮任务面板显示状态、进度、步骤、员工、详细日志与结果摘要。
- 任务、日志、正文、结构化元数据及历次更新结果持久化；失败不得写成成功。
- 已深采数据支持查看最新正文与采集元数据。

## R4 · OpenAI 兼容模型引擎

### R4.1 模型配置

- 支持 OpenAI API 兼容模型的新增、删除、修改、查询、列表和默认模型设置。
- 支持文本、图像、音频、视频、多模态和嵌入分类。
- 支持系统提示词、top_p、上下文数、最大 token 和温度配置。
- 列表 PC 一行两列、每页 6 个，支持搜索和分类筛选。
- API Key 只在服务端使用，不完整回显或进入源码包。

### R4.2 对话、SSE 与统计

- 模型对话通过独立服务层调用，不由 Controller 直连 SDK。
- 模型响应默认采用 SSE，支持增量内容、错误、完成和 usage 事件。
- 每个模型显示真实 token 用量统计，并在请求完成后更新。
- 业务调用未指定模型时自动选择唯一启用的默认模型。

### R4.3 回归要求

- 修复新建模型后 loading 不结束、按钮无反馈的问题。
- 修复模型分类点击后列表不变化的问题。
- 异步操作失败时必须关闭 loading、恢复按钮并显示可理解错误。

## R5 · 数字员工管理

- 数字员工支持新增、修改、删除、启停、搜索、列表和每页 8 条分页。
- 模型型员工可选默认或指定模型，系统提示词必填，技能与 Crawl4AI 配置可选；任务模板必须保留 `{{input}}`。
- API 型员工支持 GET/POST、公开 HTTP/HTTPS 地址、请求参数、超时及 JSON/数据卡片预览。
- 所有员工使用唯一 `@调度名`；后台工作可通过统一服务层调度，Controller 不直连外部模型或 API。
- 系统“采集专员”不可删除或停用，负责 R3.3 深度采集。
- 用户侧输入 `/` 或 `@` 可调度已启用员工，命令面板支持键盘选择；系统采集专员不暴露给普通用户。

## R6 · 用户侧问数与任务 3.4

- 所有依赖安装和运行必须位于项目 `venv`；提供一键 `setup.ps1` 与 `run.ps1`。
- 深度采集由 `@采集专员` 调用 Crawl4AI，保存标题、正文 Markdown、来源地址、状态码与采集版本。
- 用户工作台左侧展示 Logo、系统标题、默认模型和任务历史；右侧展示对话区与输入区。
- 登录、注册与后台用户管理共享同一用户/角色/状态数据，不建立第二套账号。
- 会话标题、用户消息、助手回答及数据卡片持久化，并按当前用户隔离读取。
- 内置 `@天气` 使用 wttr.in JSON，展示当前天气、体感、湿度、风况和三日预报。

## 数据关系

- `users.role_id → roles.id`：一个用户属于一个角色。
- `role_features`：角色和功能的多对多授权关系。
- `features.parent_id → features.id`：空值表示一级功能，非空表示其直属二级功能；最多两级。
- `menus.feature_id → features.id`：一个菜单绑定一个功能。
- 瞭源与规则描述请求模板；采集记录引用所使用的来源和规则。
- 数据仓库记录来源于采集结果，并以规范化业务键去重。
- 模型配置保存类型、连接信息、参数和默认状态；usage 统计关联模型。
- 数字员工可选关联模型；深采任务关联仓库数据和派发员工，日志与结果关联任务。
- 新功能禁用后，其页面、写接口和流式接口授权立即失效。

## R5.1 · 数字员工 Markdown Prompt 资料

- 新增和编辑表单支持同时上传一个或多个 UTF-8 `.md` 文件，单文件不超过 512KB、单员工最多 8 个。
- 文件按 `data/dgUser/<employee_id>/` 隔离，文件名经过安全化；删除员工时同步删除对应目录。
- Markdown 在模型型员工调用时补充到系统 Prompt，并明确标记为事实资料，不能覆盖系统指令。
- 运行时上传资料、数据库和密钥不得进入源码 ZIP。

## R6.1—R6.4 · 流式问数与数据智能

- 用户侧模型请求采用 OpenAI 兼容 `/chat/completions`、`stream=true` 和 `stream_options.include_usage`。
- `/api/chat/stream` 使用 SSE 输出 status、delta/message、usage、conversation、done/error 事件。
- 每条助手消息显示响应秒数、token 数和已配置的模型/数字员工名称；接口未提供 usage 时显示 0，不伪造。
- 天气员工按后台 `response_mode=card` 渲染天气卡片，城市路径必须百分号编码。
- 普通问数先做安全意图识别：仓库概览、来源分布、趋势、深度采集、关系图谱和报告使用真实数据库；其他问题交给模型。
- 所有统计 SQL 在 Repository 内固定定义，用户只能提供自然语言；禁止回显 SQL、执行用户 SQL或接受越权/Prompt 注入。
- 图表只在分析意图命中时生成；支持 KPI、柱状、折线、环形、关系图和表格，并提供文字/表格替代。
