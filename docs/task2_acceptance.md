# 老师任务 2 验收映射

本文把老师给出的任务 2、2.1、2.2、2.3、2.4 映射到代码、数据关系和自动测试。验收以服务端实际行为为准，页面隐藏按钮不能替代权限校验。

## 任务 2：四个权限管理模块

| 老师要求 | 实现约束 | 验收重点 |
|---|---|---|
| 用户管理 | 用户只绑定一个角色；列表、搜索、新增、修改、删除、启停、批量操作；20 条/页 | 上方搜索与批量操作、中间列表、下方分页；超过 20 条后第二页可见 |
| 角色管理 | 普通用户与系统管理员为内置角色；自定义角色可维护 | 系统管理员角色不可编辑、授权、停用或删除；列表 20 条/页 |
| 角色—功能联动 | `role_features` 保存多对多映射 | 使用本地 Layui Tree 显示一、二级功能；禁用功能不可选且不再授权通过 |
| 功能管理 | 图标、名称、路由、排序、状态和 `parent_id` | 只允许一级和二级，拒绝自引用、循环和第三级；20 条/页 |
| 菜单管理 | 菜单一对一绑定功能，只负责排序、显示和预览 | 按角色预览；左侧菜单取角色授权、功能启用、菜单显示的交集 |
| 数据关系 | `users → roles`、`roles ↔ features`、`features → menus`、`features.parent_id → features.id` | 外键、唯一约束、事务及迁移不破坏旧 ID 和授权 |

## 任务 2.1：useradmin 后台登录

复现步骤：

1. 创建编码为 `useradmin`、访问端为管理侧的角色。
2. 为该角色授予 `user_management` 功能。
3. 创建账号 `useradmin / admin888` 并绑定该角色。
4. 退出 `admin`，使用 `useradmin / admin888` 登录 `/admin/login`。
5. 打开 `/admin/users` 应返回 200；页面明确显示只读状态。
6. 构造用户新增、修改、删除或批量请求应返回 403，数据库保持不变。

验收结论：角色的管理侧范围决定能否登录后台，功能授权决定能否查看模块；是否为默认超级管理员决定能否写入四个权限配置模块。这三层判断不能混为一层。

## 任务 2.2：防止 useradmin 删除 admin

- 默认 `admin` 账号以 `is_superadmin=1` 标识，Repository 的通用更新、删除和批量方法都必须拒绝该目标。
- Controller 在进入写入前先要求当前账号为默认超级管理员，因此 `useradmin` 的合法 XSRF 伪造请求仍返回 403。
- 页面中 `admin` 行禁用选择框，不显示通用编辑、停用和删除入口；这只是可用性措施，安全依赖服务端保护。

## 任务 2.3：右上角下拉文字可读

- 账号菜单容器和链接使用显式的深色背景、浅色前景，并提供悬停与 `:focus-visible` 状态。
- 不依赖 Layui 默认的白色文字；键盘可以展开、聚焦和关闭菜单。
- 自动测试检查模板语义和 CSS 声明，浏览器验收再检查实际对比、点击区域和移动端布局。

## 任务 2.4：admin 只能本人改密

- 通用用户编辑动作不允许修改 `admin` 的任何字段。
- `admin` 行只向本人显示“修改我的密码”，专用表单仅包含当前密码、新密码和确认密码。
- 服务端以当前 Secure Cookie 中的账号作为目标，不接收任意 `user_id`；先验证当前密码，再写入新的随机盐与 PBKDF2-SHA256 哈希。
- 错误旧密码、两次新密码不一致、弱密码、非 `admin` 调用均失败。
- 用户名、角色、启用状态和超级管理员标识始终保持不变。

## 自动化与人工验收

- Repository 测试：分页、批量保护、角色保护、两级功能、禁用联动和菜单按角色过滤。
- HTTP 测试：`useradmin` 登录/只读、伪造写请求、admin 通用编辑与删除保护、本人改密、XSRF。
- 静态前端测试：Layui Tree 初始化、本地下拉菜单颜色与焦点、三段式管理布局标记。
- 终端 Playwright：在 1440×1000 和 390×844 下检查登录、用户/角色/功能/菜单页；不调用会导致桌面客户端闪退的内置浏览器。
